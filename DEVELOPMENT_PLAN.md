# План развития «Календарь звонков»

Очередь задач для OpenCode-агента в GitHub. Каждая задача оформляется как issue,
агент вызывается комментарием `/oc fix` (или `/oc explain` для triage) и ведёт
изменения в PR. Коммиты — по [Conventional Commits](https://www.conventionalcommits.org/)
(`feat:`, `fix:`), чтобы release-please собирал changelog автоматически.

## Фичи (feature)

| ID | Название | Описание | Критерий приёмки |
|---|---|---|---|
| F1 | Отмена брони гостем | Гость может отменить свою бронь (нет авторизации — по `id`+`guestEmail`) | `POST /api/bookings/{id}/cancel` возвращает `204`; слот снова свободен; отмена дважды — `404` |
| F2 | Пагинация списка встреч | `GET /api/bookings` отдаёт `{ data, meta }` с `page`/`perPage` (default 20) | При >20 бронях страницы содержат корректные элементы; `meta.total` совпадает |
| F3 | Поле «комментарий гостя» в брони | В `POST /api/bookings` добавляется необязательное `guestNote` (≤ 500 символов), сохраняется и возвращается | Бронь с `guestNote` создаётся; владелец видит заметку в списке встреч |
| F4 | Длительность типа события из `durationMinutes` | Слоты генерируются под `durationMinutes` типа (сейчас жёстко 30) | Для типа с `durationMinutes: 60` слоты по 60 минут; кратность сохраняется |

## Баги (bug)

| ID | Название | Описание | Критерий приёмки |
|---|---|---|---|
| B1 | Прошедшие слоты текущего дня | В текущем дне отдаются слоты с временем раньше «сейчас» | `GET /api/event-types/{id}/slots?date=<сегодня>` не содержит прошедших слотов; завтра/позже — все |
| B2 | 500 при брони без `eventTypeId` | `POST /api/bookings` без `eventTypeId` падает с 500 вместо 422 | Ответ `422` с понятным сообщением валидации |
| B3 | Гонка дубля брони | Два одновременных запроса на один слот могут пройти (race) | Оба запроса → один `201`, второй `409`; в БД одна запись |
| B4 | Rate limiting не на `/api/bookings` | `POST /api/bookings` не покрыт троттлингом, в отличие от `/slots` | N+1 подряд запросов → `429` (N по конфигу throttle) |

## Порядок работы агента

1. В issue — расплывчатое описание → `/oc explain` (triage), затем уточнение.
2. `/oc fix` — агент создаёт ветку `fix/F1-<slug>` или `feat/F1-<slug>`, правит код + тесты, открывает PR.
3. PR проходит ревью (общий и построчный комментарий с `/oc`), агент дорабатывает.
4. Merge → release-please формирует release-PR с changelog и версией.
